# Design notes

Rationale and invariants. Nothing here is needed to run a round, but each entry explains
why something is the way it is — read before changing any of it.

## Notes

- **Never push to protected branches** — the authoritative list is `protected_branches` in the merged config. The MR's own target branch is also off-limits regardless of whether it appears in that list. Only push to the feature branch.
- **Each fix commit must be separate** — never amend commits after a QA round is posted.
- **Fresh sub-agent per round** — each Agent tool call is a new invocation with no prior context, which is what produces unbiased findings. Never reuse a session that already reviewed the branch. This holds for the Step 3A.1 workflow path too — each round spawns a fresh reviewer panel.
- **The round is delegated to a QA manager subagent (default path)** — Step 3A.1 spawns one `qa-manager` Agent that fans out the **preflight-selected** `qa-reviewer` panel (3-6 lenses, from `preflight.json`'s `lenses` array) **concurrently** as its own Agent grandchildren, merges/renders/posts in its own context, and returns only a compact verdict to main. Lens choice is deterministic (three core lenses always + conditional lenses per the target's `lens_tags` and the live schema signal, capped at 6) — not model judgment, the same principle as `review_mode`. This replaces the earlier `Workflow`-tool fan-out to keep all lens/merge/render noise out of the main context (cleaner main loop; slightly higher total tokens — the manager is one extra agent). The panel is the default whenever the diff is non-trivial (sequential Step 3A fallback only for a tiny diff, or if Agent nesting is unavailable); `--double`/`--triple` only add second-opinion shims *inside* the manager. Every lens (and the manager) keeps the session's top-capability model — QA never downgrades to a cheaper tier; manage per-round cost via panel width and the trivial-MR skip, not model choice. `--non-interactive` (defaultable gates auto-answered) + `--auto-approve` (skips the Step 3E confirm on an otherwise-passing round) make a clean round fully hands-free — **neither flag can bypass the schema-change human-approval gate**. The review path comes from preflight's `review_mode`; the concurrency comes from the manager's Agent fan-out. **The skill does not use the `Workflow` tool at all** — the old detection step, its `workflows_supported` field, and the `detect-workflows-support.sh` helper were deleted rather than left as dead weight explaining why they were dead.
  The two reasons the Agent path is preferred, moved here out of the spine: (1) **a clean main loop** — the manager runs the whole noisy round in its own context and returns only a compact verdict; (2) **hooks reach the lenses**. Verified in this environment: PreToolUse fires inside Agent subagents at **depth 2** (a keyword-free grandchild spawn was hard-blocked by `agent-cmm-gate`), PostToolUse fires inside subagents too, and `SubagentStart` guidance reaches the manager and its lens grandchildren. So a lens's own calls are governed like the main thread's — native `Grep` on source → `grep-cmm-gate`, non-exempt large Bash → `ctx-execute-enforcer` (bare `grep` exempt). `Workflow`-tool workers reportedly **bypass** these gates (not re-verified here), which is the original reason to prefer Agent. Reviewer **correctness does not depend on any of it**: it rests on the diff, the acceptance criteria, and definition-site evidence, so the panel still works with none of that tooling present.
- **A cycle may end with findings open.** `diminishing_returns` + the Step 3E deferred-findings exit are a matched pair and neither works alone: the stop-rule tells you to stop with findings open, and the exit is what lets such an MR still be approved. Shipped without the exit (as it briefly was), the stop-rule only converted an endless cycle into a stuck one — the MR became permanently unapprovable, which is worse than the problem it solved. The price of the exit is that approval now rests on an enumerated deferral list in a posted note rather than on the absence of findings, so that note is load-bearing: a deferred finding that is not written down has not been deferred.
- **Proportionality is injected on every round, and escalates.** preflight always writes `$QA_SCRATCH/proportionality.md`; Step 3A and the manager inject it verbatim as a `## Proportionality` section of every lens prompt, by the same titled-section rule as the code-navigation mandate. It exists because the reviewer contract optimizes **recall** — assume slop, find every substantive bug — with nothing on the other side of the scale. Measured on gitops-ansible !12, a 40-line credential fix: round 1 produced 6 findings, all in the role; round 2 added a variable round 3 then removed (net zero across two rounds); round 3's fix added a 230-line test play, and **round 4 was 11 of 14 findings about that test play**. The diff grew 9x, the shipped behaviour had been correct since round 2, and no individual finding was wrong — the aggregate was worthless. The mandate stays light at rounds 1-2, where real defects still surface, and tightens at `round >= 3` where the value curve flattens. At the strict tier it also asks the lens to say outright when most of its blocking findings target code an *earlier QA round* introduced; the manager raises that as a `diminishing_returns` decision, and it is a legitimate reason to end the cycle with findings still open. A reviewer that concludes "this change is correct" has produced a complete result.
- **Code-navigation tooling is injected, never assumed** — the skill's *correctness* does not depend on CMM/context-mode being installed. preflight probes whether they are registered and writes `$QA_SCRATCH/tool-mandate.md`: a "use these" block when they are available, **empty** when they are not. Step 3A / the manager inject that file verbatim as a `## Code navigation` section of the lens prompt, so with no tooling present the prompt says nothing about it and the lens simply uses Read/grep — the review is correct either way. The agent *definitions* stay tool-agnostic; the tool names live only in preflight's mandate emitter. (Delivery detail that matters: the mandate must land as a **titled `## Code navigation` section**. Measured on a real diff — no mandate: 0 tool calls; the same text as a detached preamble above a `---` divider: 0, ignored; as a titled section: ~9. Adoption is substantial but stochastic, not exhaustive.)
- **The fixer gets its own mandate, separate from the reviewers'** — preflight writes a second file, `$QA_SCRATCH/fix-mandate.md`, read by the orchestrator in Step 3B. It is deliberately *not* appended to `tool-mandate.md`: that file is injected into every lens spawn prompt, reviewers are forbidden from prescribing fixes, and the titled-section adoption effect measured above is worth not diluting. The asymmetry it corrects: the lens reviewers read the code deeply and are barred from fixing it, while the orchestrator — which has a findings list, a context full of round artifacts, and possibly no reading of the file at all — holds the pen. It was the only participant never handed a navigation mandate, and it is the one that must find every site.
  Unlike `tool-mandate.md`, this file is **never empty**. When a graph is available it mandates a freshness check *first* — a stale index answers `trace_path` with the callers of the pre-MR code and reports no other sites, which is an absent check reporting as a pass, and worse than grep because it fails silently rather than noisily. When no graph is available it says so and requires the round note to describe reconciliation as best-effort. Site discovery via regex is not equivalent: it misses a renamed alias, a re-export, a call split across lines, and an inconsistent spelling, and it misses all of them without signalling. Even with a graph, config, migrations, templates, fixtures, docs, runtime-built call names, dynamic dispatch and reflection are outside it — hence the explicit `search_code` residue sweep, and the language caveat that `CALLS` edges are heuristic outside the LSP-resolved families.
- **`scope` and `diff_scope` were once the same key.** jq keeps the *last* of a duplicate key, so the registry string was silently destroyed and every consumer went back to re-reading the config by hand — the exact work preflight exists to remove. preflight now asserts `.scope|type=="string"` before it will emit, and a test locks it, so the spine no longer carries the warning. The same reasoning is why the subproject block is named `layout` rather than `project`.
- **A round in flight reports progress, because silence and death used to look identical.** preflight seeds `$QA_SCRATCH/status` — one pipe-delimited line, `mr|target|round|phase|done|total|epoch_start` — and the manager rewrites it as each lens returns, also dropping that lens's raw findings in `$QA_SCRATCH/lens-<name>.json`. Measured motivation: on the first real end-to-end run the panel spent 20+ minutes writing nothing at all, so an operator could not distinguish six working lenses from a manager that had died, and diagnosis came down to reading agent timers in the UI. The per-lens files double as the manager's recovery point — five completed reviews no longer die with the sixth.
  `lib/statusline-fragment.sh` renders that line for a statusline. Three constraints shape it: it prints **nothing** when no round is in flight (it runs on every repaint of every session, so an idle tax is unacceptable); it costs one glob and one read, which is why the line is written pre-formatted rather than parsed out of `preflight.json`; and **staleness is a state, not an absence** — a crashed round leaves its scratch dir behind forever, so freshness comes from the file's mtime and a round that stops updating is reported as `⚠stalled`, not silently shown as healthy. `phase=done` and an abandoned directory both go quiet. Compose it into an existing statusline; it is deliberately a fragment, never a whole `statusLine`, because clobbering a user's own is not a reasonable price for this.
- **Findings on the cycle's own fixes are attributed and reported — never acted on.** Each round's note carries a `QA-Fix-Commit: <sha>` trailer; preflight reads those back from prior notes into `qa_fix_commits`, and `lib/attribute-findings.sh` marks every finding sitting on a line one of them wrote. Two or more blocking findings so marked, and the note says so under its heading. Measured motivation: on one real 5-round cycle, three of five rounds found a defect the previous round's fix introduced, twice critical.
  **Why `git blame` and not a line-range comparison.** The obvious design — record the lines each fix commit touched, then test whether a later finding falls inside one — is wrong: insertions and deletions between rounds shift every line below them, so round 3's `foo.js:120` bears no relation to line 120 as round 1 touched it. Blame is computed against the content at the reviewed HEAD, so git does the tracking. Its limits all under-report, which is the safe direction for a signal that only informs a human: blame attributes the *last* touch (an author edit over a QA line hides it), deleted code cannot be blamed at all (a fix that removed something is invisible), and a round that merely reindented an earlier round's line takes the attribution — the specific round can be wrong while the aggregate stays right.
  **Why the trailer rather than matching commit subjects.** `fix(scope): address QA round N` is preflight-rendered and therefore predictable, but rebases, squashes and hand-edited messages all break subject matching. The round note is already the cycle's durable ledger — the same principle the deferred-findings exit runs on — so the SHA goes there.
  **Why it does not recommend reverting.** Deliberate, and the operator's explicit call. A round's fixes share one commit, so reverting to undo one bad fix also undoes the good ones beside it; the author's own commits must never be caught in it; and the decision turns on whether the premise was wrong or the execution sloppy, which the attribution cannot distinguish. The tool reports the pattern; the human decides. `diminishing_returns` and the deferred-findings exit already provide the way to end a cycle once they have.
- **Panel cost is roughly comparable to a serialized review, not N× it** — moved out of the spine, which only needs the resulting rule. The bulk of a review's tokens is iterative tool-call reasoning (read → search → reason); the panel *splits* that across lenses rather than duplicating it, so cumulative (context × turns) is roughly conserved. The premium is in the margins: each lens re-reads the same diff (no shared prompt cache), each carries its own preamble, and the manager is one more agent. So a manager-owned round costs a little **more total tokens** than the old Workflow path while keeping that spend, and the whole merge/render, **out of the main context** — it fixes context pollution, not raw token count. On a large read-heavy diff the read portion trends additive per lens. The levers are **panel width** (preflight-selected 3-6; narrow a target's `lens_tags` rather than overriding by hand) and the **trivial-MR gate** — never the model tier, because a cheaper reviewer is a weaker reviewer.
- **preflight renders the manager's spawn brief; the spine no longer transcribes it.** `$QA_SCRATCH/manager-brief.txt` (`manager_brief_path` in the JSON) carries the ~25 values that do not depend on the invocation's flags. Previously the model copied them out of `preflight.json` into a text blob on every round of every MR: per-invocation cost for a mechanical transformation, an error surface nothing tested (a dropped field stays invisible until the manager misbehaves), and a spine paragraph per field explaining why that field is passed. Only flag-dependent values are still passed at spawn (`post_note`, `non_interactive`, `DOUBLE`/`TRIPLE`, `reviewer_override`, `skip_contract_verification`). The suite now asserts the *whole* key set, which is the check that hand-transcription could never have.
  `approval_eligible` moved the same way. It is `round >= min_clean_round OR (tiny_relax AND is_tiny)` — all three inputs already in preflight — yet the spine asked main to compute it at runtime and documented its own failure mode: omit it and the manager can never raise `approval` or `sast_wait`, so the hands-free path silently never approves anything. Eligibility remains *necessary, not sufficient*; Step 3E re-checks every gate.
- **The manager's contract lives in `agents/qa-manager.md`, not in the spine.** The spine carried ~40 lines of "hard invariants the manager MUST satisfy" — verdict shape, merge axes, failed-lens handling, full-context-per-lens, never-downgrade — every one of which was already in the agent definition the manager actually reads. Main loaded it on every invocation and acted on almost none of it. The spine now keeps only main's own consequences (arm the schema gate, treat an all-dead panel as a failed round) and the cost guardrail.
- **Fixes are verified with the PROJECT'S own test/build rules, discovered rather than configured.** `lib/detect-verify.sh` finds the target's entry point (Makefile `test:` target, `scripts.test`, tox.ini, `go.mod`, …); preflight emits it as `verify.{state,command,source,build_command}` and Step 3B runs it before the fix commit. Configuring the command here instead would duplicate something the project already declares, and the duplicate drifts — the gate would keep running a command the project abandoned and report a pass. `verify.command` remains as an override for when detection is simply wrong, empty by default.
  Two rules came from running the detector against real repos, and the obvious implementation violates both. (1) **A manifest's presence proves nothing**: one real submodule ships a `package.json` with an empty `scripts` object beside a Makefile holding the actual `test:` target, so "package.json exists → npm test" emits a command that always fails. Every detector tests for the real entry and falls through when it is absent. (2) **Finding nothing is a result**: `state=none-found` is reported, never blanked, because a project with no runnable tests is precisely the project whose QA fixes go unchecked. `init check` reports this per target so the gap is raised against the *repo*, where it can be fixed, rather than surfacing mid-round.
  The gate also requires that a new or changed test be shown to FAIL without the fix. This is the specific hole behind the tail-chasing pattern: a test written alongside a fix, never run against the unfixed code, passes for the wrong reason and certifies nothing while looking like proof. Measured on one real 5-round cycle, three of five rounds found a defect introduced by the previous round's fix, twice critical.
- **Subproject vocabulary is gated on there being subprojects.** preflight emits a `layout` block — `multi_target` (more than one configured target), `target_count`, and `target_is_submodule` (asked of git via `--show-superproject-working-tree`, not inferred from the target's path or name). Step 4 names the target only when `multi_target`, and mentions the parent-workspace commit only when `target_is_submodule`. An earlier version keyed the reminder on the target being named `monorepo` — one organisation's target name, meaningless in any other repo, and the kind of literal that survives an extraction unnoticed. Telling someone with a single-root repo to update a parent workspace describes a structure they do not have; the same reasoning makes `TARGET` an optional argument and leaves `.commit_subject` scopeless (`fix:` not `fix():`) when there is only one project.
- **Switching trunks vs. patches:** This now happens automatically when you switch monorepo branches — each branch carries its own `.branchconfig.yaml` declaring its base branches. The project config is only edited to add/remove a target or change its path/remote/scope, or to update the `qa_agent` / `sast_gate` / `security_stage` policy. A `_production_reference` block in a project config is historical and can be removed once every active monorepo branch has a `.branchconfig.yaml`.
- **Two GitLab identities:** QA notes and approvals run under the QA agent token (the `qa_agent` block in the merged config); git pushes and fix commits stay on the user's dev token. If the QA agent token is missing, the skill degrades gracefully — posts notes with the dev token and skips approval.
